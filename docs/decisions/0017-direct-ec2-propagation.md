# 0017: Direct EC2 propagation with cycle fencing

Status: accepted for implementation at the operator's request; activation requires an offline deployment review.

The operator requested that generation agents use EC2 APIs instead of a CloudFormation stack for every successor. This implementation is reconciled against `saraislet/cloud-glider` main at `8e773fc`, including shared lifecycle controls, operator switches, separate generation state, cleanup-only scheduled retries, and persistent SDK clients. It supersedes the CloudFormation-only agent invariant for explicitly selected EC2 cycles. Existing CloudFormation cycles remain supported; changing backend during a live cycle is prohibited.

CloudFormation still manages the retained control plane, the operator-owned persistent launch template, and generation zero (`cfn/ec2-seed.yaml`). The agent uses `RunInstances` with exactly one instance and a positive numeric launch-template version. CONTROL pins the account, template ID, version and canonical SHA-256 of EC2's `LaunchTemplateData`. Static user data pins the seed and agent artifacts. Creation tags carry the cycle, generation, predecessor and deterministic handoff token. EC2's immutable `aws:ec2launchtemplate:id` and `aws:ec2launchtemplate:version` tags establish the launch-template identity; `DescribeInstances` has no launch-template property.

The backend is explicitly `ec2` and the continuation model is `EC2_DRY_RUN_THEN_RETIRE`. The default remains CloudFormation for compatibility with existing initialized environments. Direct generations use reusable SDK clients and the existing lifecycle schema 2. CONTROL retains approved settings and operator switches; BOOTSTRAP/REQUEST owns propagation and cleanup gates. Every state mutation is fenced by the exact cycle. GEN state and exact resource inventory stay in the separate generation table, and audit writes replace latest-event records rather than accumulate records.

Before launch, an atomic transaction checks the lifecycle, operator stop/cleanup switches and HOLD, then writes a non-expiring provisioning marker plus durable submission intent. A lost EC2 response must be reconciled with the matching actual instance. An intent with no matching instance cannot be automatically reissued. Inventory is persisted before clearing the marker; cleanup waits for provisioning to settle. Tokens include the cycle so a later lifecycle cannot adopt a former instance.

Readiness remains distinct from EC2 running status. Fresh candidate heartbeats must match lineage, artifact identity and control state. Handoff checks the exact candidate snapshot, CURRENT identity, unexpired lease, controls and lifecycle in one transaction. Continuation uses an unexecuted `RunInstances(DryRun=True)` request, accepting only `DryRunOperation`, plus live-count, account vCPU and subnet-capacity checks. Dry run proves request authorization, not future EC2 capacity. At max_generation the boundary substitutes for another launch.

For this backend, retirement is serialized: after handoff the child verifies ownership and continuation proof, terminates its exact predecessor, and waits for confirmed termination before continuing. This deliberately suspends the overlap optimizations in decisions 0005 and 0006 for EC2 cycles. Two live instances are preferred; the absolute inventory ceiling remains three, including shutting-down instances. Stop and HOLD preserve the predecessor. Missing EC2 results are never proof of deletion.

The agent role is tagged with its selected backend. Foundation inline policies and managed permission boundaries select the same backend through CloudFormation conditions; each expanded variant stays within AWS policy-size limits. Direct policies scope RunInstances to the approved launch template, image, subnet, security group, profile and small instance type. Direct mode denies legacy CloudFormation provisioning, launch-template mutation, network mutation and IAM mutation. PassRole is limited to the existing agent role and EC2. The bootstrap cleanup controller can terminate only tagged direct generation instances; code additionally checks cycle, immutable template identity and recorded client token before deletion. It preserves the persistent launch template, verifies residual volumes and resource deletion, and uses the existing cleanup retry mechanism.

This is a source change, not an AWS deployment. IAM fixtures and SDK model validation cannot prove live authorization. The existing optional Organizations SCP candidates encode the CloudFormation-only contract and must not be attached unchanged to an EC2 deployment. Their redesign and any deployment-principal policy changes require separate security administration review; this change does not alter workflows or deployment roles. See `docs/ec2-propagation.md` for activation and recovery.
